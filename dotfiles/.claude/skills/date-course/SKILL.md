# 데이트 코스 추천 (Date Course Recommender)

사용자에게 지역·시간·취향에 맞는 **실제 가게가 포함된, 동선이 현실적이고 기억에 남는 데이트 코스**를 여러 선택지로 제안한다.
모든 출력은 **한국어**로 한다. 기본 지역은 한국이다.

> 코스 조립·순서·마무리는 **아래 "설계 원칙(근거 기반)"** 을 따른다. 이게 "그냥 장소 나열"과 "좋은 코스"를 가른다.

## 1단계 — 입력 수집

다음 3가지가 필요하다. 처음 요청에서 안 준 항목이 있으면 **AskUserQuestion으로 물어본다** (이미 준 항목은 다시 묻지 않는다).

1. **지역/장소** — 예: "서울 성수동", "부산 서면"
2. **시간대 / 소요시간** — 예: "오후 2시부터 4시간", "저녁 데이트"
3. **취향 / 분위기** — 예: "감성 카페", "활동적/액티비티", "조용한", "맛집 위주", "실내 위주(비 옴)"

세 가지가 모이기 전에는 코스를 만들지 않는다.
- **예산·관계 단계**(첫 데이트인지 오래된 커플인지)는 사용자가 먼저 말하면 반영하되, 없으면 굳이 묻지 않는다. 단, "첫 데이트" 신호가 있으면 5단계의 **안전 배려**를 자동으로 얹는다.

## 2단계 — 실제 가게 검색 (카카오 로컬 + 웹)

서로 성격이 다른 코스를 만들려면 후보가 넉넉해야 한다.

> **키 설정 (최초 1회):** 카카오 REST API 키가 필요하다. 환경변수 `KAKAO_REST_API_KEY` 또는 스킬 폴더의 `.kakao_key` 파일에 저장한다(발급: https://developers.kakao.com → 내 애플리케이션 → 앱 키 → **REST API 키**). 키가 없다는 에러가 나오면 이 설정을 사용자에게 안내한다.

**1순위: 카카오 로컬 검색 스크립트** — 실제 존재하는 가게를 정확한 주소·좌표·카테고리·전화번호와 함께 반환한다. 여러 카테고리를 **한 메시지에서 병렬 `Bash`로** 호출한다.

```bash
python3 ~/.claude/skills/date-course/kakao_search.py "성수동 감성 카페" --size 15
# Windows(cmd/PowerShell)라면: python "C:\Users\<이름>\.claude\skills\date-course\kakao_search.py" "성수동 감성 카페" --size 15
```

- 검색어는 **`<지역/동> <카테고리 명사>`처럼 단순하게** (예: `성수동 카페`, `연남동 맛집`, `성수동 전시`). 카카오는 "저녁"·"조용한" 같은 수식어에 약하다 — 실측: `연남동 저녁 맛집` 0건, `연남동 맛집` 1,456건. 분위기는 검색어가 아니라 후보 선별과 WebSearch에서 반영한다.
- **0건이면 수식어를 떼고 재검색**한다. 그래도 없으면 인접 동/역 이름으로 넓힌다.
- **카테고리 코드로 정밀도↑**: `--category CE7`(카페) · `FD6`(음식점) · `AT4`(관광명소) · `CT1`(문화시설). 카페/맛집/명소를 구분해 뽑을 때 검색어에 얹어 쓴다.
- **후보 풀 확대**: `--pages 3`으로 여러 페이지를 모아 중복 제거된 후보를 넉넉히 확보한다(한 번에 최대 15건 한계 극복).
- 좌표로 반경을 좁히려면 `--x <경도> --y <위도> --radius 2000`(m), 가까운 순 정렬은 `--sort distance`. 첫 검색에서 얻은 앵커 가게의 x/y를 쓰면 **동선이 실제로 붙는 후보**만(각 항목에 `거리 Nm` 표시) 뽑을 수 있다.
- 스크립트가 반환한 **주소·좌표를 그대로 신뢰**한다 (동선·이동시간 판단의 근거). 지어내지 않는다.

**2순위 보강: `WebSearch`** — 카카오는 "어디 있는지"엔 강하지만 "요즘 평판·분위기·추천 이유"는 약하다. 후보를 추린 뒤 **최신 리뷰/블로그/영업정보 확인용으로** 병렬 웹 검색을 얹는다 (예: `성수동 ○○카페 후기 2026`).

검색 카테고리 예시 (분위기 키워드를 반영):
- 카페 / 디저트 · 식당(점심/저녁) · 산책/명소/포토스팟 · 액티비티/체험/전시/실내

소요시간에 맞춰 장소 개수를 정한다 (대략 2시간=2곳, 4시간=3곳, 종일=4~5곳). 코스 2~3개를 만들 것이므로 카테고리별 후보를 2곳 이상 확보한다.
가능하면 **몰입형·체험형 활동(원데이클래스·방탈출·전시 등)** 후보를 하나는 확보한다 → 안티-퍼빙(아래 원칙)에 쓰인다.

### 검색 품질 · 정확도 규칙
- 가게 이름·주소·좌표는 **카카오 결과를 우선**한다. **웹에서 찾은 후보는 반드시 카카오 검색으로 존재를 교차 확인**한다 — 블로그 추천 가게가 카카오에 없으면 폐업/이전일 가능성이 높으니 제외한다.
- **최신성 확인 (위험도 기반)**: 코스에 넣을 개인 가게는 **2024년 이후 리뷰·언급**이 있는지 `WebSearch`로 확인한다. "폐업/영업종료/이전/임시휴업" 신호 → **제외**. 언급을 못 찾았을 뿐이면(소규모 가게는 흔함) → 검증된 대체 후보로 교체하거나, 유지하되 "☎ 방문 전 영업 확인 권장"을 표기한다. 체인점·백화점·공공시설(공원·미술관·전망대)은 웹 확인을 생략해도 된다.
- **위치 교차 확인**: 카카오 주소로 실제 그 지역/동에 있는지 확인. 동명이점을 잘못 넣지 않는다.
- 확인 못 한 장소는 **지어내지 말고** "○○ 인근 카페"처럼 유형으로만 두고 재확인 필요를 표시.
- **지역-취향 불일치**: 요청 취향을 그 지역이 못 채우면(예: 연남동 + "야경") 억지로 끼워 맞추지 말고 **솔직히 알린 뒤** 가장 가까운 대안(노을 산책, 루프탑, 인근 지역 스팟)을 제시하고, 원하면 지역을 넓힐지 물어본다.

## 3단계 — 동선 + 순서 설계 (코스 조립)

후보를 **하나의 현실적인 동선**으로 엮되, 아래 원칙에 따라 **순서까지 의도적으로** 정한다.

**동선(공간):**
- **근접성 우선**: 장소들을 가깝게 묶는다. 도보 15분 이내 기본, 멀면 대중교통/차 시간을 명시. 지역을 가로지르는 backtracking을 피하고 **한 방향으로 흐르게**.
- **이동 명시 + 체류시간**: 장소 사이마다 이동수단·소요시간을, 각 장소엔 체류시간을 넣고, 합이 사용자의 소요시간에 맞는지 확인.
- **동선 계산으로 검증 (지어내지 말 것)**: 코스 정류지 순서를 정했으면 그 좌표들을 `route_util.py`에 넣어 구간별 도보시간과 **총 이동시간(도보 + 대중교통 추정 포함)**을 계산하고, 그 값을 4단계 출력의 이동시간에 쓴다. "대중교통 권장" 구간의 추정치는 참고값이니 실제 노선·시간은 웹으로 확인해 명시한다.

```bash
python3 ~/.claude/skills/date-course/route_util.py "127.0557,37.5445" "127.0631,37.5471" "127.0668,37.5443"
```


**순서(시간·감정) — 근거 기반:**
- **🎯 피크엔드**: 가장 강렬한 긍정 순간(야경·노을·특별한 디저트·하이라이트 활동)을 **맨 끝(피날레)** 에 배치하고, 중반에 또렷한 피크를 하나 둔다. 최고 장소를 맨 앞에 몰지 않는다. *(기억은 피크와 엔딩이 지배 — Kahneman)*
- **완급(리듬)**: 정적(카페·식사)과 동적(산책·체험) 활동을 번갈아 배치. 활동적 블록 뒤에는 **회복+대화 구간**(카페·느린 산책)을 둔다. 고각성 블록은 데이트당 1~2개로 제한.
- **설렘 뒤 친밀**: 신나는 활동(체험·액티비티) **직후**에 가까이 앉아 대화하는 구간(조용한 카페·바)을 붙인다. *(흥분전이 — 각성이 상대 호감으로 전이)*
- **타이밍(외부 시계)**: ①경치·포토스팟은 **노을 30~40분 전**에 도착하게. ②식사는 배고파지기 전, 러시 직전에(줄·행그리 회피). ③인기 장소는 붐비는 피크를 피함. → **거리 순이 아니라 최적 시간 순**으로 정렬.

## 4단계 — 코스 선택지 구성 (출력)

**서로 성격이 다른 코스 2~3개**를 만든다 (예: A=감성/여유, B=활동적, C=맛집 투어). 각 코스:

```
### A안 · <컨셉 한 줄> (예: 감성 카페 데이트)
🗺️ 동선: <출발지> → <2번째> → <피날레>  (총 이동 도보 20분 내외)
💰 예상 비용: 1인 약 3~4만 원

- ⏰ 14:00  <실제 가게 이름> — <추천 이유 한 줄> (체류 약 1시간)
- 🚶 이동 · 도보 8분
- ⏰ 15:10  <실제 가게 이름> — <추천 이유> (체류 약 1시간 30분)   🎯 피크
- 🚇 이동 · 지하철 2정거장 6분
- ⏰ 16:50  <실제 가게 이름> — <추천 이유> (체류 약 1시간)   🏁 피날레(야경/노을 등)
```

- 각 코스 머리에 **🗺️ 동선 요약** + **💰 1인 예상 비용대**(못 찾으면 "가격 확인 필요").
- 중반 하이라이트에 **🎯 피크**, 마지막에 **🏁 피날레**를 표시해 왜 그 순서인지 드러낸다.
- 시작 시각은 사용자 시간대에 맞추고, 각 장소에 **추천 이유 한 줄 + 체류시간**을 붙인다.

**🖼️ HTML 카드(선택):** 마크다운 코스를 제시한 뒤 "카드(HTML)로 저장/공유할까요?"를 제안한다. 사용자가 원하면 확정 코스를 위 스키마의 JSON으로 만들어 `render_course.py`에 넘기고, 생성된 HTML을 `SendUserFile`(display: render)로 전달한다. 타임라인·🎯피크/🏁피날레 배지·Plan B·팁·카카오맵 링크가 든 한 장짜리 카드가 나온다.

```bash
python3 ~/.claude/skills/date-course/render_course.py course.json -o course_card.html
# 실제 지도까지 넣으려면(선택): --js-key <카카오 JavaScript 키> 또는 스킬 폴더의 .kakao_js_key 파일
```

- 입력 JSON 스키마·필드는 `render_course.py` 상단 docstring 참조 (title·meta·courses[].stops[] 등, 대부분 선택 필드).
- 지도는 기본 **링크만**(키 불필요). JS 키가 있을 때만 마커+경로 지도를 임베드한다. ⚠️ 이건 로컬 HTML 파일이며 Artifact가 아니다(카카오 지도 JS는 Artifact CSP에 막힘).

**🔗 연인 공유 링크(선택):** 폰에서 열어 연인에게 보낼 수 있는 GitHub Pages PWA 링크를 함께 제시한다. HTML 카드와 **동일한 JSON**을 그대로 쓰며, 코스 데이터가 URL에 담겨 서버 저장이 없다(링크를 아는 사람만 열람). 로컬 HTML은 저장용, 이 링크는 카톡 공유용.

```bash
python3 ~/dev/projects/date_course_selection/share_link.py course.json
# → https://leegwanhui.github.io/date-course-selection/#... (그대로 연인에게 전달)
```

- 렌더러·인코딩 규약은 `date_course_selection` repo의 `docs/`(PWA) + `share_link.py`에 있다. Pages 배포가 안 돼 있으면 링크는 배포 후 동작.
- 코스 JSON에 `courses[].factors: ["peak-end","novelty",...]`(선택)를 넣으면 PWA에서 **심리 근거 칩**으로 뜬다(탭 → 요인 설명). slug 목록은 repo `build_web_data.py`의 `SLUGS`. 안 넣어도 🎯피크/🏁피날레 배지가 있으면 peak-end 칩이 자동으로 붙는다.

**💞 우리 데이트 기록(선택):** 사용자가 "기록에 저장"을 원하면 확정 코스를 아카이브에 넣어 지난 데이트를 모아볼 수 있다. ⚠️ **아카이브는 Pages에 공개**되므로(파일로 커밋됨) 비공개는 위 공유 링크(URL 해시)를 쓴다.

```bash
python3 ~/dev/projects/date_course_selection/save_course.py course.json --slug seongsu-first --date <YYYY-MM-DD>
# → docs/courses/<slug>.json 저장 + index.json 갱신. PWA 홈(파라미터 없는 URL)이 목록으로 보여줌
```

## 4.5단계 — 코스별 복장 추천 (fashion 연동, 선택)

`~/dev/projects/fashion`이 있으면, 확정 코스마다 그 코스 조건에 맞는 복장 한 벌을 함께 제시한다.
fashion repo가 없으면 이 단계를 건너뛰고 "복장 추천은 fashion repo가 있을 때만 됩니다"만 한 줄 알린다.

1. `~/dev/projects/fashion/profile.md`를 읽어 상태 확인.
   - 상태가 `미완성`/파일 없음 → 복장 추천을 하지 않고 "style 스킬로 진단을 먼저 하세요"라고 안내.
2. **날씨를 여기서 조회한다**(5단계 Plan B가 재사용): 데이트 날짜의 예보 기온·강수를
   `WebSearch`로 확인(`<지역> 날씨 <날짜>`). 날짜 미지정 또는 조회 실패면 **계절 기본값**으로
   후보를 좁히고 복장 블록에 "예보 확인 못 함"을 한 줄 표시한다.
3. `~/dev/projects/fashion/date_outfit.md`를 읽고, 코스마다 **컨텍스트 7항목**을 채운다:
   계절·기온·강수 / 시각(낮→저녁 전환) / 총 보행거리·이동시간(route_util 값) / 실내외 비중 /
   격식 상한(코스 중 최고 격식 장소) / 옷 위험요소(물·모래·먼지·기름) / 관계 단계(있으면).
4. `date_outfit.md`의 1·2단계 + 항상-적용 3규칙으로 복장을 고른다. 아이템의 **보유 여부는
   `wardrobe.md`로 확인**하고, 없는 옷은 "가진 것 아님"을 표시한다.
5. 코스별로 출력에 복장 블록을 붙인다:
   ```
   👔 복장 · A-3(여름 데이트) 기반
      네이비 폴로 + 베이지 투턱 치노 + 흰 독일군 + 브라운 벨트
      ⚠️ 총 보행 4.2km — 공식의 로퍼 대신 흰 독일군으로 (저녁 바엔 로퍼가 격에 맞지만 4km를 못 이김)
      ↳ 밝은 톤 상하 + 브라운 소품은 검증된 조합
      ✓ 반팔은 넣어 입기
   ```
   `⚠️`는 조정이 있을 때만. 표에 안 맞는 코스(수영·등산 등)는 억지로 맞추지 말고 범위 밖이라고 말한다.
6. HTML 카드/공유 링크를 만들면 그 코스의 복장을 `courses[].outfit`에 넣는다(조정 후 최종 구성):
   `{formula, items, swaps?, why?, checks?}`. ⚠️ **why·swaps·checks에 체형 실측·인상 목표를
   쓰지 않는다** — 카드가 연인에게, 아카이브는 Pages에 공개된다. 아이템 이름·코스 기반 이유까지만.
7. **코스를 확정했을 때만**(공유 링크/카드 생성 시) `~/dev/projects/fashion/log.md`의
   `## 대기 중`에 한 줄 등록한다. A/B/C 제시만 한 시점엔 등록하지 않는다.
   형식(style 스킬이 읽는 형식 그대로, **조정 후 최종 아이템**으로):
   ```
   - YYYY-MM-DD(요일) 데이트 · <아이템 나열> → 반응 미확인 (만료: 추천일+14일)
   ```
   추천이 바뀌면 최종 것만 남긴다. 이 등록으로 다음 style 상담이 착용 반응을 물어 루프에 합류한다.

## 5단계 — 마무리 안내

- **☔ Plan B 한 줄**: 실외 위주 코스라면 **4.5단계에서 확인한 예보**(복장 추천을 건너뛴 경우엔 여기서 `WebSearch`로 확인: `<지역> 날씨 <날짜>`)를 근거로, 비/더위/추위가 예상되면 근처 실내 대체 장소를 한 곳 제안한다. 날짜 미지정이면 계절 리스크만 짚는다.
- **📵 몰입 팁(안티-퍼빙)**: 체험형 활동이 들어간 코스면 "폰 내려놓고 몰입하기 좋은 코스"임을 한 줄로 짚어준다. *(파트너 퍼빙은 만족도를 크게 낮춤 — 2024~26 연구)*
- **📸 여운 팁**: 피날레에서 사진 한 장 정도로 가볍게 기록하길 권한다(내내 찍기보다). *(피크엔드 강화 + 여운)*
- **🔒 안전 배려(첫 데이트/초기)**: 공공장소·각자 이동·적정 음주 정도를 자연스럽게 권한다. 초기 단계에서만, 과하지 않게.
- **예약·확인**: 인기 맛집·전시 등은 미리 예약을 권함.
- 필수 안내 한 줄: **"영업시간·휴무·예약은 방문 전에 꼭 재확인하세요 (웹 정보라 바뀌었을 수 있어요)."**
- 가능하면 각 가게의 출처 링크/검색 근거를 함께 제공.
- 마지막에 "특정 코스를 더 자세히 짜줄까요? 아니면 조건을 바꿔볼까요?"처럼 다음 행동을 제안.

## 설계 원칙 (근거 기반, 요약)
좋은 데이트 코스를 가르는 핵심. 위 단계에서 이미 적용하지만, 판단이 필요할 때 이 원칙으로 되돌아온다.
- **피크엔드**: 하이라이트를 끝에. 짧고 강한 마무리가 길게 끄는 것보다 낫다(지속시간 무시).
- **완급 + 회복**: 정·동 교차, 활동 뒤 대화 구간. 과자극·단조로움 둘 다 피한다.
- **흥분전이**: 설렘 활동 직후에 친밀한 대화 구간을 붙인다.
- **자기확장(새로움)**: 둘 다 처음인 경험 하나를 넣으면 만족·친밀감이 오른다. '비싼'보다 '새로운'.
- **대화 설계**: 활동으로 화제를 만들고, 조용한 착석 구간에서 깊은 대화로. 마주/코너 좌석.
- **개인화**: 상대 취향을 반영한 작은 서프라이즈 하나를 끝 근처에. 여러 개보다 하나.
- **타이밍·안전·안티퍼빙**: 노을/식사/혼잡 시간 최적화, 초기엔 안전, 몰입형 활동으로 폰 멀리.
- 항상: **실제로 검색으로 확인한 가게만** 쓰고, 취향을 반드시 반영하고, 출력은 스캔하기 쉽게.

*근거 상세: 심리학·관계학 리서치(peak-end rule, self-expansion, excitation transfer, partner phubbing 연구 등) 기반. 전체 리서치는 date-course-selection 리포트 참조.*
